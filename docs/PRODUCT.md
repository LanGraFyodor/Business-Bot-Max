# Продукт и проверка гипотезы

Docspace решает типичную для небольших команд проблему: документ отправляют в один чат, замечания обсуждают в другом, итоговое решение теряется между версиями. В Docspace команда разбивает работу на каналы; каждый документ хранит файл, версии, обсуждение и решение руководителя. Основной сценарий с телефона: открыть команду → канал → документ → отметить замечание → отправить на согласование → получить решение.

Целевая аудитория: малые агентства, проектные команды и отделы, уже работающие в MAX. В демо представлены две вымышленные команды и вымышленные документы. Наличие этих данных не означает интеграцию с корпоративными системами.

## Проверяемая гипотеза

Если документ, обсуждение и согласование находятся в одном мобильном рабочем пространстве, сотрудник быстрее находит актуальную версию и реже пересылает файл повторно. Для пилота с 2–3 командами предлагаем измерять:

- долю документов с финальным решением внутри Docspace;
- медианное время от отправки на согласование до решения;
- долю возвратов, после которых загружена новая версия;
- число запросов «где последняя версия?» в рабочих чатах до и после пилота.

Это целевые метрики пилота, фактических измерений пользователей пока нет.

## Границы MVP

Реально реализованы команды, одноразовые адресные приглашения MAX-аккаунтов с выбранной ролью, отзыв доступа, каналы и сообщения, роли, документы и версии, комментарии, согласование и возврат, поиск и мобильный UI. Полномочия проверяются на сервере для каждого запроса. Бот работает через официальный MAX API; токен проверен запросом /me. Через одного бота можно создать команду, пригласить сотрудника или руководителя по MAX ID, вступить, сменить роль и исключить участника до публикации мини-приложения. Прикладной UI протестирован локально в браузере. Для проверки внутри MAX требуется публичный HTTPS URL и привязка к боту организаторами.

Интеграции с ЭДО, CRM, хранилищами компании, OCR и AI-проверкой не реализованы. Вместо корпоративных данных используются синтетические примеры. Внутреннее согласование не заменяет юридически значимую электронную подпись.

## Техническая траектория

MVP использует один Go-процесс и локальное хранилище JSON+файлы. При росте нагрузки: PostgreSQL для команд, событий и поискового индекса; S3-совместимое хранилище файлов; очередь уведомлений; журнал аудита; резервное копирование; антивирусная обработка загружаемых файлов. Прежде чем подключать реальные организации, нужны эксплуатационные настройки: постоянный HTTPS, мониторинг, резервные копии и политика хранения данных.

Исходный код организован по слоям: `cmd/docspace` — запуск, `internal/app` — бизнес-правила и HTTP, `web/src` — клиент. Контракты — `docs/openapi.yaml`. Значимые сценарии проверяются Go-тестами и отдельным браузерным тестом.
